# Wargame – procedural RTS map generator

Procedural terrain generator for a **multiplayer (2–4 players) modern-military RTS**.
Current scope: map generation + rendering + RTS camera only (no units/gameplay yet).
The generated `Terrain` object is meant to be consumed by future gameplay and AI code.

## Working with files

- **Prefer Claude Code's built-in tools** (`Read`, `Write`, `Edit`, `Grep`, `Glob`) over shell commands. Read files with `Read`,
  search with `Grep` / `Glob`, change content with `Edit` / `Write`. Don't `cat` / `sed` / `awk` / `echo >` files, and never edit
  source through Python (or other) scripts or `sed -i`: built-in edits are reviewable and fail loudly when the text doesn't match.
  Use `Bash` for what only a shell does (pnpm scripts, git, running the app / Node scripts, screenshots).

## Finding symbols: graphify first

- **Search symbols, files and relationships through graphify before reading source code.** Use `graphify query "<question>"`,
  `graphify path "<A>" "<B>"` and `graphify explain "<symbol>"` (graph in `graphify-out/graph.json`, summary in
  `graphify-out/GRAPH_REPORT.md`) to locate where something is defined, what calls it and what depends on it.
  Only then `Read` the specific files / line ranges the graph points to. Fall back to `Grep` / `Glob` only when graphify
  has no answer (new or renamed symbol, non-code text).

## Keeping graphify up to date

- **After every implementation** (any change that adds, removes, renames or moves code, docs or skills), refresh the graph
  before finishing: `/graphify . --update` (or `graphify update .` for code-only changes, which needs no LLM).
- Do this as the last step of the change, after typecheck / verification, so the graph matches the final code.
- If the graph is missing or stale beyond an incremental update, rebuild with `/graphify .`.

## Stack & commands

- TypeScript everywhere, **pnpm** only. Three.js (r186), Alpine.js (UI panel), Vite 8, `vite-plugin-glsl`.
- `pnpm dev` → http://localhost:3000 (port fixed, `strictPort`; the user may already be running it). Runs `textures:ensure` first.
- `pnpm build` (textures + `tsc --noEmit` + vite build), `pnpm typecheck`, `pnpm preview` (also port 3000).
- `pnpm textures` regenerates all PNG textures (`--force`); `textures:ensure` only writes missing ones.
- Node ≥ 23.6 runs `.ts` directly (type stripping): **imports must use `.ts` extensions**, and only erasable
  TS syntax is allowed (`erasableSyntaxOnly`, no enums/namespaces/parameter properties).
- `public/assets/**` is tracked with **Git LFS** (`.gitattributes`). Textures are generated by
  `scripts/generate-textures.ts` (own PNG encoder, tileable noise, fixed `TEXTURE_SEED`).
- The app generates `{ size: 640, cell: 2 }` (`MAP_SIZE` / `MAP_CELL` in `engine.ts`, play area ≈ 1278 m); `generateTerrain` itself
  defaults to size 256. Test with the app's options.

## Core rules

1. **Determinism**: same integer seed (0..2^32-1) ⇒ identical map. All randomness goes through
   `mulberry32` / `hash32` (`src/core/rng.ts`). Never use `Math.random()` in generation.
2. **Per-module random streams**: `src/terrain/seeds.ts` → `STAGE = { sea:1, shape:2, detail:3, rivers:4,
   ranges:5, rocks:6, roads:7, cover:8, trees:9, bases:10, rails:12, cities:13, buildings:14, lighthouses:15, towers:16, power:17 }`
   (11 retired, never reuse). Each module gets `stageRng(seed, STAGE.x)`.
   **Never renumber**; add new stages with new numbers so other modules' output doesn't shift.
   Render-side cosmetic randomness (tints, shapes) is also seeded (`hash32(seed, salt)` / fixed seeds).
3. Generation is pure TS with no Three.js dependency (`src/terrain/**`) so it can run in Node / workers / server.
4. Heavy Three.js objects must stay out of Alpine reactivity; `engine.generate()` returns a plain `MapInfo`.
5. **Everything drawn must support distance LOD and be cheap far away** — no detail is needed in the distance. Every
   new generated content type gets a near / far representation (mesh `lodMin` / `lodMax`, sprites, simplified far mesh,
   or hidden beyond a distance), and every shader fades its fine detail (patterns under ~1 m, thin lines, extra texture
   taps) to an average colour with `surfaceDetail()` (`shaders/chunks/lod.glsl`) and **skips computing it** beyond the
   range. Sample textures only where their blend weight is > 0 (`textureGrad` with gradients taken outside the branch).
   Shadows follow the same levels (the shadow pass culls with the sun frustum but picks LOD from the main camera); a
   far level that can't cast (sprites) gets a low-poly `userData.shadowOnly` caster. Check a new shader / generator for
   this before calling it done.
6. **Every light source and lit object goes through the `LightField` and gets a far-visibility halo.** Never add ad-hoc
   `THREE.PointLight` / `SpotLight` or a private glow for lamps, windows, signals, flashes, etc.: register `LightDef`s in a
   `LightGroup` (`world.lights.createGroup()`; `group.build(defs, grid)`), which gives the deferred light (or the cheap overlay
   quads on `low`), the light rays for spots and the **light halo** (`lighthalo.*`, a camera-facing disc that stays a few pixels
   wide and fades in with distance, so lit things stay visible when their models / windows are culled). Set the halo range with
   `group.setHaloRange(start, end)` so the halo is at full strength before the near model is culled (halos start *close*: ~0.1x
   to 0.4x of the model's draw distance). Emissive things that don't fit a `LightDef` (e.g. per-window lights) need their own halo
   instances with the same fade (`buildingHalo.vert`). Drive on / off with `group.level` (daylight etc.). See skill `render-lighting`.
7. **Anything placed on the map must register its footprint** so later modules keep off it: add cells to `ctx.clear` (rocks, trees),
   level ground only before dependants are built, and make later planners (street lights, poles…) avoid it. See skill `terrain-pipeline`.

## Coordinates

- Grid: play area `size` vertices per side + `pad = 64` cells on every side => `N = size + 2*pad` vertices, `cell = 2` world units,
  `worldSize = (N-1)*cell`, centred on origin (app: size 640 ⇒ N = 768, worldSize 1534, play area 1278 m; default 256 ⇒ N = 384,
  worldSize 766, play area 510 m). `Terrain.play` = playable square in grid cells (`i0..i1`, `j0..j1` = `pad`..`pad+size-1`). Camera bounds = play area.
- **Whole grid is generated the same way** (relief, rivers, roads, buildings, cover, rocks, trees). Only three things are
  tied to the play area: edge mountain ranges (start at the play area border and run outward to the grid edge), bases
  and cities (inside it). Sea coasts are measured from the play area border too (sea fills the margin beyond). River bridges /
  crossing sites are planned inside the play area only. Noise-driven modules use play-area-relative coordinates.
- Heightmap layout `heights[j * N + i]`; `i` → +X (west→east), `j` → +Z (north→south). World `x = i*cell - worldSize/2`.
- `WATER_LEVEL = 0`, `SNOW_LINE = 80` (shared by generator and terrain/rock shaders; snow patches start ~12 m lower, `SNOW_MARGIN`;
  snow slides off faces steeper than ~40°). 1 world unit ≈ 1 m. Sides: `north`=j=0, `south`=j=N-1, `west`=i=0, `east`=i=N-1.
- `sampleGrid(h, N, x, y)` = bilinear sample at fractional grid coords. Building / site local frame: local +Z (front) points along
  (sin yaw, cos yaw) in world XZ, local +X along (cos yaw, -sin yaw).

## Pipeline at a glance

`layout → relief → rivers → bases → cities → roads → buildings → landmarks → power → cover → rocks → trees` (`src/terrain/pipeline/stages.ts`),
one shared `GenContext`, streamed as `GenEvent`s to the renderer (`src/render/pipeline/`). Output must stay bit-identical between
`generateTerrain` and the streamed events. Details: skills `terrain-pipeline` (all stages), `render-architecture`.
